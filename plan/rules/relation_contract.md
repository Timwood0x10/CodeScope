# CodeScope Relation Type Contract

> Status: **Authoritative**
> Owners: engine + store + query modules
> Last updated: 2026-07-31

## 1. Purpose

This document is the single source of truth for how SQLite `relation.type`
integers map to LadybugDB `CALLS` / `RELATES` tables and to the
`graph::EdgeType` enum. Production code MUST NOT branch on raw integer
thresholds such as `rtype >= 4`. It MUST call the helpers declared in
`engine/src/graph/graph_types.h`.

## 2. Canonical Type Table

| `relation.type` | `graph::EdgeType`     | LadybugDB table | Semantic                                  |
|-----------------|-----------------------|-----------------|-------------------------------------------|
| 0               | `References`          | RELATES         | Non-call symbol reference                 |
| 1               | `Calls`               | **CALLS**       | Function / method invocation              |
| 2               | `Defines`             | RELATES         | Definition relationship                   |
| 3               | `Contains`            | RELATES         | Structural containment (class → method)   |
| 4               | `Imports`             | RELATES         | Import / include                          |
| 5               | `Inherits`            | RELATES         | Class inheritance                         |
| 6               | `UsesType`            | RELATES         | Entity uses a type                        |
| 7               | `HasType`             | RELATES         | Type definition has fields/methods        |
| any other       | (mapped to References)| RELATES         | Unknown kinds — safe non-call fallback    |

The `RELATES` table retains its `edge_type` column so callers can
distinguish References from Defines, Contains, Imports, etc.

## 3. C++ API

Declared in `engine/src/graph/graph_types.h`:

```cpp
namespace graph {

EdgeType relationTypeFromInt(int rtype);
int      relationTypeToInt(EdgeType type);

bool isCallsEdge(int rtype);
bool isCallsEdge(EdgeType type);

bool isRelatesEdge(int rtype);
bool isRelatesEdge(EdgeType type);

} // namespace graph
```

- `isCallsEdge(rtype)` returns `true` iff `rtype == 1` (`EdgeType::Calls`).
- `isRelatesEdge(rtype)` is the logical complement.
- `relationTypeFromInt` maps unknown integers to `EdgeType::References`
  so an out-of-range value can never accidentally pollute `CALLS`.

## 4. LadybugDB Mapping Rules

1. Only `EdgeType::Calls` is written to the `CALLS` table.
2. Every other typed relation is written to `RELATES` and keeps its
   `edge_type` column.
3. The split point in `store_graph_compiler.cpp` MUST use
   `graph::isCallsEdge(rtype)` — never a raw integer comparison.
4. `getCallers` / `getCallees` Cypher (Step 1 onward) MUST restrict to
   `CALLS` and assert `r.edge_type = 1`.

## 5. Legacy `graph_edges.edge_type` Numbering (DEPRECATED)

The legacy `graph_edges` table uses a different numbering:
- `1` = `call_graph`
- `3` = `symbol_reference`

The legacy fallback path in `store_graph_compiler.cpp` is being phased
out and only runs when `entity`/`relation` tables are empty. New code
MUST NOT use this numbering; it MUST go through the canonical
`relation.type` contract above.

## 6. Accuracy Metric Definitions

The accuracy benchmark (Step 2 onward) uses these definitions, recorded
here so they cannot drift between implementers:

- **TP (True Positive)**: an actual CALLS edge that is in `expected_calls`.
- **FP (False Positive)**: an actual CALLS edge that is not in
  `expected_calls` and not in `allowed_unresolved` / `external_calls`.
- **FN (False Negative)**: an `expected_calls` edge missing from actual.
- **Precision** = `TP / (TP + FP)`.
- **Recall** = `TP / (TP + FN)`.
- **F1** = `2 * P * R / (P + R)`.
- **contamination_rate** = non-Calls edges / total edges returned by
  callers/callees. Must be 0%.
- **duplicate_rate** = duplicate `(project_id, source_id, target_id,
  type)` rows / total `relation` rows. Must be 0%.
- **sqlite_ladybug_diff** = `|{CALLS in SQLite relation(type=1)} △
  {CALLS in LadybugDB}|`. Must be 0.

## 7. Fixture Identity Rules

To keep fixtures portable and immune to database ID drift, every
fixture entity is identified by the semantic tuple:

```
file_path + qualified_name + kind + start_row
```

Database IDs (`entity.id`, `relation.id`) MUST NOT appear in fixture
ground truth. Step 7 introduces a stable entity UID API; until then
the semantic tuple above is the canonical identity.

## 8. Baseline Snapshot

The baseline snapshot for `dev@eca4bd0` is generated by
`engine/tests/test_accuracy_baseline.cpp` (added in Step 0). It records:

- `relation` row counts grouped by `type` (0–7).
- LadybugDB `CALLS` / `RELATES` row counts grouped by `edge_type`.
- Duplicate `(project_id, source_id, target_id, type)` count.
- Pass/fail status of the 13 existing accuracy tests.

The baseline is intentionally recorded BEFORE the Step 1 query
tightening so subsequent steps can produce before/after diffs.
