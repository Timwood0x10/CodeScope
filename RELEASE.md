# CodeScope v0.2.7


Pre-tag hardening pass: closes the remaining silent-failure paths (code_rules §1) on the default release path, adds self-healing to the shared-store lock, and removes dead code. It also brings `index-parallel` to Windows.

Edge counts for THIS repository are quoted as measured at the point each entry describes — the graph moved as the fixes in those entries landed (`2214`, `2242`, `2259`), and `benchmarks/baselines/graph_self.json` (`2269` edges) is the authoritative final shape. Counts for the other projects (goagent, pyo3, tinygo, redis, petclinic, `ts-codebase-memory-mcp`) are A/B measurements of one change and are quoted per entry.

### 🚀 New Features

- **Counterfactual factor switch for resolver tuning** (`engine/src/resolver/factors.{h,cpp}`, `engine/src/resolver/pipeline_apply.cpp`): `CODESCOPE_RESOLVER_DISABLE_FACTOR=<Name>` drops one factor's contribution — its weight and its score both — at the single `acc()` choke point every factor goes through, so measuring a factor needs one environment variable and no code edit, and `deciding` can never name it. An unknown value is reported on stderr once with the list of valid names, because a typo would otherwise look like "this factor changes nothing". Why it exists: `relation.reason` records the factor with the largest contribution (`decided_by=`), and on this repository that field names ImportMatch for every one of the 1201 scored edges, which suggests the ranking is dominated by the largest weight rather than by discriminating evidence. The counterfactual shows the two questions are different, and that only one of them predicts a graph. Measured by disabling each factor in turn and diffing edge identities — this repository (C++, 2216 edges) and tinygo (Go, 4313 edges): ImportMatch moves 604 removed / 179 added (C++) and 326 / 270 (Go); DefinitionMatch 516 / 47 (C++); ReceiverMatch 146 / 10 (Go); ModuleMatch 6 / 34 and NamespaceMatch 4 / 34 (C++, 19 / 2 each in Go); SignatureMatch 11 / 30 (C++, 3 / 4 in Go); DistanceMatch 18 / 2 in Go but 0 / 0 in C++; and ConstructorMatch, CallKindMatch and CommonNamePenalty only ever ADD edges when disabled (0 / 32, 0 / 33, 0 / 32 in C++), i.e. they suppress wrong candidates rather than create right ones. **ImportModuleMatch is the exception that proves the metric wrong**: on the TypeScript project it IS the largest contribution for 19 edges, and disabling it changes the graph by exactly 0 edges — the field measures the weight table, the switch measures the outcome. No weight is changed until this table says otherwise.
- **Graph-shape regression baselines** (`benchmarks/graph_baseline.sh` (new), `benchmarks/baselines/graph_*.json` (new), `make bench-graph` / `bench-graph-update`, `benchmarks/README.md`): the existing benchmarks measure speed, so a visitor or resolver-factor change could add, drop or re-point edges on real projects while every unit test stayed green — the unit tests pin hand-built fixtures, and the three visitor fixes in this release were found by hand-written fixtures, not by a gate. The new script indexes fixed checkouts and compares the canonical shape of the resulting graph against a committed baseline: files, entities, call edges, call sites, the `resolution_kind` distribution, the call-site `resolve_strategy` distribution, the `deciding_factor` distribution (parsed from `relation.reason`) and the unresolved-site count. One project per language, so a change that helps Go and hurts Rust is visible instead of averaged away: `self` (C++), `c-redis` (C), `go-tinygo` (Go), `java-spring-petclinic` (Java), `rust-pyo3` (Rust) and `ts-codebase-memory-mcp` (TypeScript + C) — six projects, six baselines under `benchmarks/baselines/graph_*.json`. Java was absent from the first pass: `index-parallel` discovers modules through `discover::discover_modules`, whose engine-supplied skip rules drop `sample`, `samples`, `example`, `examples`, `test`, `tests` and `docs` at depth 3 and deeper, so spring-petclinic — whose entire source tree lives under `src/main/java/org/springframework/samples/petclinic/` — reported `note: "no source modules found"` and indexed nothing, while `codescope discover <same path>` counted all 49 files. That inconsistency is fixed in this release (the policy behind `engine_path_is_skipped` now learns the project's language the way the indexer does — see the Maven/discovery entry below), so the Java baseline is back and the script's `PROJECTS` list and `benchmarks/README.md` both record the story.

- **`index-parallel` (and `chunk-worker`) now work on Windows** (`server/src/scheduler/mapped_file.rs`, `shm.rs`, `chunk_queue.rs`, `src/main.rs`): both schedulers coordinate the parent process with worker subprocesses through a `#[repr(C)]` state block in a shared file, and both open-coded the POSIX sequence `open` + `ftruncate` + `mmap(MAP_SHARED)` — which is why the whole parallel path was `#[cfg(not(windows))]` and every Windows user silently fell back to single-process indexing. The mapping now lives in one place, `MappedFile`, with two backends behind the same contract ("create sizes the file to exactly `len` and returns an all-zero, cross-process view; the owner removes it on drop"): POSIX keeps `mmap`, Windows uses a file-backed section object (`CreateFileMappingW` + `MapViewOfFile`, torn down with `UnmapViewOfFile` + `DeleteFileW`). Windows leaves the bytes of an extended file undefined, so that backend zero-fills explicitly rather than relying on `ftruncate`'s guarantee. Both queue implementations lost their duplicated mapping code and their hand-written `Drop`. `windows-sys` is added as a `cfg(windows)` dependency (the version `walkdir` already pulls in).
- **The parallel scheduler no longer assumes `/tmp`** (`server/src/scheduler/{mod,chunked,dyn_config}.rs`): the per-run DB prefix and the queue segment path are built from `std::env::temp_dir()` via new `temp_path`/`default_db_prefix`/`default_shm_path` helpers. Windows has no `/tmp`, so the first write would have failed there; the unit tests that used literal `/tmp` paths follow suit, since they also run on Windows hosts.
- **`dev.yml` gained a native-Windows smoke job** (`windows-smoke`, `workflow_dispatch`): it installs MinGW and the `sqlite3` CLI, builds `x86_64-pc-windows-gnu`, and indexes a real project through both schedulers, asserting a non-empty graph. The existing cross-compile job only proves the binary links; the chunk queue is a runtime property of two Windows processes mapping one file. **This job has not run yet** — it is dispatch-only until its first green run.

### 🐛 Bug Fixes

- **`detect_changes` answered "nothing changed" for a file that had** (`engine/src/query/impact_analysis.cpp`, `engine/tests/test_query_algorithms.cpp`): the modified-file list reaches the engine as the caller spells it, while the lookup is an exact `entity.file_path IN (...)` against the stored form — and that form is canonical, because `createProject()` registers a project root through `weakly_canonical`. A relative path, or an absolute one that passes through a symlink, therefore matched no row and the tool returned `{"modified":[]}` with no error, i.e. reported a changed file as unchanged. Measured on this machine: `/tmp/dc/src/main.go` and `src/main.go` both found nothing while `/private/tmp/dc/src/main.go` found both functions, and the same shape reproduced on the 428-file TypeScript project. Each entry is now matched in two forms — verbatim, and anchored at `projects.root_path` then resolved through the store's own rule (`store_core.cpp normalizeRootPath`, now shared as `util::resolvePath`) — because the same measurement that fixed `file_filter` showed databases holding the caller's un-resolved spelling, and dropping the verbatim form would have made the tool report "nothing changed" for those instead. Verified across all three spellings on the scratch project and through a relative path on the TypeScript project; the new test covers the relative and symlinked forms and creates its own symlink, so it does not depend on macOS's `/tmp`.
- **`shortest_path` and `codescope_trace` advertised no required arguments** (`server/src/tools/catalog.rs`, `server/src/tools/mod.rs`): both handlers resolve their endpoints and reject a call without them — `h_shortest_path` calls `resolve_endpoint` once per end and answers `either 'from' (symbol name) or 'from_id' (node id) is required`, and `codescope_trace` answers `{"error":"empty symbol name"}` — while the catalog declared no requirement at all, so a client that read `tools/list` called with `{}` and got an error the schema could have prevented. The rule is "the symbol NAME or the node ID", which `required` cannot express, so each endpoint is stated as an `anyOf` and the two ends are combined with `allOf` (`codescope_trace`: `function_name`, or `from` + `to`). Pinned by a new assertion in the catalog's test module so the requirement cannot be dropped silently again.
- **A failing engine test could pass the gate** (`engine/tests/test_check.h`, `engine/tests/test_query_algorithms.cpp`): the shared header documents the contract "the success path must end with `return checkFailures() ? 1 : 0;`" and states the consequence in the same breath — "without that, the failure is only printed and the test still exits 0, which `make test-engine` would read as a pass" — and 8 of the 106 engine test files call `CHECK`/`CHECK_MSG` while never consulting the counter at all (`grep -L checkFailures engine/tests/test_*.cpp`, intersected with the files that use the macro): a failing check inside them was invisible to a gate that judges by exit code. The contract is now enforced instead of asked for: `reportFailure()` registers an exit hook that flushes and exits non-zero when any check failed, so a `main()` that forgets the epilogue can no longer pass, while a test that records nothing still exits with whatever it returns (verified with a probe that returns 0 after a failed check — exit 1 — and one that returns 0 after passing checks — exit 0; the flush matters because `make check` redirects stdout to a file, and `std::_Exit` does not flush, which would have thrown away the failing test's own output). `test_query_algorithms.cpp` also printed its `PASSED` banner unconditionally; it now prints it only when no check failed, which is how a red run came to be read as green before the hook existed.
- **`find_definition`, `find_references`, `find_callers` and `find_callees` missed a symbol whose file was named through a symlink** (`engine/src/query/query_engine.cpp`, `engine/src/util/path_util.h`): each wraps the caller's `file_filter` — documented as "optional: absolute file path" — in `file_path LIKE '%'||?||'%'` against rows that hold the resolved absolute path, and used the argument verbatim, so an absolute path that reaches the project through a symlink matched nothing and the query answered `{"results":[],"total":0}` for a symbol that exists. Reproduced on a real index: after indexing `/tmp/pn/real`, the filter `/tmp/pn/link/src/main.go` returned no result while `/private/tmp/pn/real/src/main.go` found it (the `/tmp` → `/private/tmp` case is masked by luck, because one form is a substring of the other, so only an arbitrary symlink name exposes it). Each filter now matches TWO patterns — the value as given and, for an absolute path, its resolved form (`util::lookupPatterns`). The given form has to stay, because the stored rows are not guaranteed to be resolved either: `createProject` resolves the root it registers, but an index driven through the engine API keeps whatever prefix the caller passed (measured — `test_homonym_filter`'s fixture indexes `/tmp/...` and holds `/tmp/...` rows, while the CLI-indexed ones hold `/private/tmp/...`), so resolving the filter alone traded a miss on one database for a miss on the other: that first version turned `test_homonym_filter` red while fixing the symlink case. Relative and partial values are never resolved, since resolving "src/main.go" or "main.go" against the working directory would turn a working filter into a wrong one. The resolution step itself moved into `util::resolvePath`/`util::lookupPath` (`engine/src/util/path_util.h`) — one implementation, shared with `createProject`'s project-root normalisation (`store_core.cpp`) and with the `detect_changes` fix above, instead of the two independent copies that existed after that fix.
- **An aliased import resolved to nothing** (`engine/src/ir/translators/js_visitor.{h,cpp}`, `engine/src/ir/translators/js_visitor_calls.cpp`, `engine/tests/test_import_alias_resolution.cpp` (new)): `import { pick as pickLib } from '../lib/helper'` binds a LOCAL name to an imported symbol, and only the local name appears at the call site. The visitor recorded the module binding (`emitImportBinding(pickLib, "../lib/helper")`, kind=21) but not which symbol the alias stands for — the `import_specifier` branch kept only the last identifier — so `pickLib()` named no declaration at all and produced NO edge. A bare call is now emitted under the imported symbol (the receiver/namespace paths are untouched: `ns.fn()` names `fn` with `ns` as its receiver, and a default import has no second name), so it resolves like any other call to that symbol. The new fixture puts the same symbol name in two modules on purpose, so the edge must reach the module the symbol was imported from rather than the same-named sibling — the exact case the ImportModuleMatch factor exists for, and the one where it is now the deciding evidence. Measured: the graph is byte-identical on the TypeScript baseline project (`ts-codebase-memory-mcp`), where the shape does not occur — its only aliased imports are namespace-style (`import { ScrollArea as ScrollAreaPrimitive }` followed by `ScrollAreaPrimitive.Root`, which the receiver path already handled) — so this is a correctness fix whose real-world frequency is still unmeasured.
- **A call that omits a default argument lost its edge, and a template instantiation was canonicalised to the wrong type** (`engine/src/resolver/factors.h`, `engine/src/resolver/pipeline_apply.cpp`, `engine/src/engine_index_metrics.cpp`, `engine/tests/test_function_arity.cpp`, `engine/tests/test_receiver_type_canonical.cpp`): both were found by rebuilding the commit before this work and diffing call edges over six real projects — the tests were green through both, because no fixture had a C++ default argument or a smart-pointer receiver. (1) The arity factor penalised a call whose argument count differed from the candidate's parameter count, but C++ declares a default in the HEADER and omits it in the DEFINITION, and the definition is where the entity and its `arity` come from: `bool FilterPolicy::loadIgnoreFile(const std::string &project_root, bool append)` is `arity = 2` while `loadIgnoreFile(root)` is a valid one-argument call, so the call scored `kScorePenalty` and `policyFor -> loadIgnoreFile`, `indexProjectImpl -> loadGitignore`, `insertFileResultBatch` and every other default-using call disappeared. Only supplying MORE arguments than are declared is impossible, so the mismatch is now a partial match in the languages that have defaults (C++, Python, JS/TS, Java — new `allowsDefaultArguments`), while Go, Rust and C keep the penalty that removes genuine same-name candidates (`New(a)` against a three-parameter `New`). The producer now also counts a defaulted parameter as an open count where it can see one. (2) `canonicalTypeName` stripped a trailing argument list, turning `std::unique_ptr<FilterPolicy>` into `unique_ptr` — a name that matches nothing, which turned calls the resolver used to resolve by unique name into lost edges and added false ones elsewhere. Which name owns the method depends on the template (`std::vector<int>` holds its own, `std::unique_ptr<Store>` forwards to `Store`), so an instantiation is now UNKNOWN rather than guessed: measured on this repository, -85 / +62 edges with the stripping against -57 / +74 with it removed, and the fixture asserts `std::unique_ptr<FilterPolicy>` is unknown. Verified end to end on six real projects (C++, C, Go, Java, Rust, TypeScript), rebuilt previous commit against this one: pyo3 2645 → 2859 call edges with its entity count 5070 → 8586 (Rust parameters now carry their type), tinygo 4386 → 4313, redis 27495 → 27474, this repository 2242 → 2259, spring-petclinic 0 → 33 (its discovery fix), TypeScript 8438 → 8440; every sampled removal is a cross-file same-name guess (`builder/*.go -> builder/uf2.go|split`, `noxfile.py -> noxfile.py|check_changelog`) and every sampled addition has a matching call. `make bench-graph` matches all six freshly written baselines and `make check` is green.
- **`index-parallel` could not index a Maven tree at all** (`engine/src/filter_policy.{h,cpp}` (new `applyProjectLanguageContext`), `engine/src/engine_filter_ffi.cpp`, `engine/src/engine_index_discover.cpp`, `engine/tests/test_filter_policy_depth.cpp`, `server/src/discover.rs`): the test/docs/samples skip names collide with Java package components, so the engine relaxes them to a top-only (depth ≤ 3) check — but only for a policy that KNOWS the project is Java, and the file that would reveal it (`src/main/java/org/springframework/samples/petclinic/Owner.java`) lives under a directory the any-depth branch skips. Verified: petclinic indexes 30 files / 137 nodes / 33 edges with `src/test` still excluded, `discover-modules` agrees with `discover` about which directory holds the sources, a `src/main/java/<name>/X.java` tree is counted for any package name, and a tree with no `.java` file keeps the default context so `pkg/a/test/x.go` stays skipped. The Java graph baseline is back in `benchmarks/`, and `benchmarks/README.md` records the whole story.
- **The same call shape resolved for Go, Java and Python and was silently DROPPED for C++, Rust and TypeScript** (`engine/src/ir/translators/{c_visitor,rust_visitor,ts_visitor,js_visitor}.{h,cpp}`, `engine/tests/test_resolver_language_consistency.cpp` (new)): the resolver disambiguates two types that declare the same method name by comparing the call's `reference.receiver_type` against each candidate's declaring type, and every visitor already reports the same call fact (`name=method, call_kind=1, receiver_text=o`). What they did not agree on is the receiver's TYPE: it was `*GoOwner` / `JavaOwner` / `PyOwner` for Go, Java and Python, and EMPTY for C++, Rust and TypeScript. The cause is the same in all three — a parameter is a declaration, but only `declaration`/`variable_declarator` nodes fed the visitors' `var_types_` table, so `CppOwner *o`, `o: &RsOwner` and `o: TsOwner` never bound a type; a call through such a parameter then had no evidence to choose with and the ambiguity gate abstained. That is a false NEGATIVE (`ToString`, `begin`, `clone` and friends are exactly the names two types share), invisible to every existing test: `test_graph_call_precision.cpp` builds hand-made records that only carry a language LABEL, and `test_ir_edge_coverage.cpp` pins what each visitor EMITS, not what the shared resolver then does with it. Each visitor now records its parameters: C/C++ walks the `function_declarator`'s `parameter_declaration` children (`type` field + `extractName`), Rust reads each `parameter`'s `type`/`pattern` and emits the same `TypeRef` + `recordVarType` pair as its local-declaration path, TypeScript reuses its existing `extractTsTypeAnnotation` for `required_parameter`/`optional_parameter`. Two candidate-side gaps had to go with them: Rust recorded methods with the bare name as the whole `qualified_name`, and TypeScript (through the shared JavaScript visitor) did the same, so even a KNOWN receiver type had no distinguishable candidate — `impl` methods are now `<ImplType>::<method>`, and the shared visitor qualifies class methods with `currentClassName()`, which gives JavaScript the same treatment. The new test writes the same three-part fixture — a typed-receiver call with a same-named decoy, an unresolved receiver whose method nothing declares — in all six languages and asserts, per language: the call reaches the parameter type's method, never the decoy, and produces no edge at all when there is no evidence; the languages that resolve are counted and asserted as an equality, so the test was RED on each of the three fixes until the corresponding visitor was corrected (it also prints the `receiver_type` it measured). Verified end to end: 6 of 6 languages now resolve to the owner's method (`goS1`→`GoOwner.Method`, `cppS1`→`CppOwner::Method`, `javaS1`→`JavaOwner::method`, `pyS1`→`PyOwner.method`, `tsS1`→`TsOwner::method`, `rsS1`→`RsOwner::method`) with zero edges to any decoy, and on this repository's own C++ tree the change moves 2197 → 2208 edges (+19/−8) where every removal was a call resolved to a same-named FIELD (`size`, `ptr`) and every addition is a real call; two runs of one binary over one tree produce identical edge sets.

- **`param_count` was 0 for every function, and `arity` — the input the resolver's overload step reads — had no producer at all** (`engine/src/engine_index_metrics.{h,cpp}`, `engine/tests/test_function_arity.cpp` (new)): `computeMetricsFromCST` counted parameters by walking the flattened records for `RecordKind::Parameter`, but no Visitor ever emits one — `semantic_records` contains no kind=8 row on any real project — so the count was structurally 0 while `cyclomatic`/`lines`/`cognitive` were correct (goagent: 6163 function entities, 0 with `param_count > 0`), and the unit test that looked like it guarded this (`test_index_metrics.cpp`, `CHECK(m.param_count == 2)`) covers only `computeMetricsFromUnit`, the legacy IR path the indexer no longer runs, as its own header states. Coverage on goagent: 4678 of 6163 function entities now carry a real `param_count` and `semantic_records` carries 12700 function arities, both 0 before. Re-indexing both real projects with and without the change moves goagent's resolved call graph by 18 removals / 9 additions (a second run measured 19 / 11; the per-edge mechanism is the same in both), and every one checks out: each removal is a same-named candidate whose parameter count cannot accept the call (`New(fabric, executors, tracker)` named by a 1-argument call, `Mutate(ctx, parent)` by a 3-argument one, `Diagnostics(agentID)` by a 0-argument one), and each addition satisfies `reference.arity == entity.arity` with a real reference row behind it (`applyRemoveNode(ctx, id)` → `RemoveNode(ctx, id)`, `ProvideRuntime(…)` → `New(config, eventStore, memManager)`, `buildDreamCycle(…)` → `NewDreamCycle(…)`). Migrated to the builder: `engine_get_capabilities`, `engine_get_type_info`, `engine_get_routes` (`engine_ffi.cpp`), `engine_index_batch`, `engine_get_project_info`, `engine_reset_parse_failures` (`engine_ffi_index.cpp`), `engine_get_knowledge_graph`, `engine_find_connected_components` (`engine_ffi_graph.cpp`), and `engine_build_evidence` (which had its own duplicate escaper). Error envelopes across the `engine_ffi*.cpp` / `engine_verify*.cpp` files now escape `e.what()` and store-error text (previously concatenated raw, so a quote in an error message produced malformed JSON). The remaining hand-built JSON in the query/store layers is now migrated to `util::JsonWriter` and the duplicate `jsonEscape` definitions/declarations are gone; escaping goes through `util::jsonEscapeString` only.
- **Dead pre-cached statements** (`engine/src/store/store_core.cpp`, `store.h`): three `sqlite3_stmt*` members prepared in `open()` with the return value ignored and never used are removed; the live per-thread statement cache (`getCachedStmt`) is unaffected.
- **`source_scope_id` cleanup `sqlite3_step` is logged** (`engine/src/store/store_batch.cpp`) and a stale “`_staged_metrics` removed” comment (the table is created and used) is dropped.
- **The Windows prerequisites now name the `sqlite3` CLI** (`README.md`): the parallel and chunked schedulers merge their worker databases by piping SQL into `sqlite3`, which the platform table did not list — and it still described parallel indexing as unavailable on Windows, which the mapping layer above had already changed. The row lists MinGW, the `x86_64-pc-windows-gnu` target, cmake and the CLI, describes the parallel path as implemented with `windows-smoke` as its acceptance gate, and points at `codescope index` for machines without the CLI.
- **Engine state moved into an explicit container and the globals are gone** (`engine/src/engine_context.{h,cpp}`, TD-1 knives 1–2): the three process-global singletons (`g_store`, `g_query`, `g_parser`) now live in one `EngineContext`. Knife 1 introduced the container and kept the old names as reference aliases so no call site had to change; knife 2 then migrated **all 340 internal call sites** to `engineContext().store` / `.query` / `.parser`, deleted the aliases, and turned the namespace-scope instance into a function-local static — so no global object is constructed before `main()` and a stale call site is now a compile error instead of a silent second path to the same state. Verified per batch with a byte-identical differential tool matrix (43 tools against a fixed DB) plus the full suites; re-indexing the engine sources then produced exactly one graph delta — 85 added `→ engineContext` call edges from the new accessor's own callers, with no pre-existing edge changed or lost. Knife 3 completed the migration by making the ABI handle-based and deleting the accessor (next entry).
- **The engine ABI is handle-based: the state is now passed in, never looked up** (`engine/include/engine.h`, `engine/src/engine_context.{h,cpp}`, `engine_lifecycle.cpp` and 19 other engine translation units; `server/src/ffi/{decls,mod}.rs`, 4 integration tests; TD-1 knife 3): `engine_create(db_path)` returns an opaque `engine_t`, **all 73 stateful entry points take it as their first parameter**, and `engine_destroy()` releases it (`engine_destroy(NULL)` is a no-op, so a failed create needs no guard). Inside the engine the 45 `extern "C"` entries resolve the handle once (`EngineContext *ctx = engineInstance(handle);`) and pass it to the 35 helpers that used to reach for the accessor, so a null handle reaches the same `engine not initialized` envelope every entry point already returned before the old `engine_init()` had run — a caller that ignores a NULL can never dereference it. `engine_context.h` forward-declares its member types and defines both special members out-of-line, so the store-only translation unit still includes it without pulling `parser.h`/`query_engine.h` in. The Rust side owns the instance: `ffi::init` installs the handle — releasing any previous instance, so the index path's re-initialisation can no longer leave a store open behind the caller's back — and `ffi::shutdown` releases it; the 54 bound wrappers keep their signatures. `engine_get_graph` was exported for the MCP graph viewer but missing from the public header (which is why the header-driven migration could not see it, and why only the linker caught the drift in the integration tests); it is declared there now. **Evidence:** the 43-tool differential matrix on a fixed 1764-node database is byte-identical between the old and the new binary (and reproducible run-to-run), re-indexing the same 185-file tree with both binaries yields the **same 1850 call edges** (`diff` empty), `make test-engine` (106 binaries) / `make test-server` (136) / accuracy gate TP 36 FP 0 FN 0, clang-format + `cargo fmt`/`clippy -D warnings` clean, and no file crosses the 1000-line limit. **Still process-wide, and therefore still a limit on two *independent* engines:** the verifier registry, the async knowledge builder's thread/flags, and the store's index-progress and parse-failure buffers — recorded in `engine_context.h` and in the header's handle contract instead of being implied by the word "instance".

### ✅ Testing

- **C++ tests no longer rely on `assert()`** (`engine/tests/test_check.h`, 35 test files): `assert()` is compiled out under `-DNDEBUG`, so an assert-based test was vacuous in any Release/RelWithDebInfo build. Every engine test now uses `CHECK()`, which is always evaluated, prints `file:line` plus the failing expression and lets the test continue; each `main` ends with `return checkFailures() ? 1 : 0;`, so one broken expectation fails CI instead of printing and passing. 929 `assert()` call sites migrated. `-UNDEBUG` is kept on test targets as defence in depth (`engine/CMakeLists.txt`).
- **Real FFI end-to-end test** (`server/tests/test_graph_ffi.rs`): indexes a Python file through the C ABI and asserts the symbol is discoverable, instead of only checking the JSON envelope on an empty DB.
- **Rust index → query end-to-end test** (`server/tests/test_index_e2e.rs`): indexes the shared Python accuracy fixture into a temp dir and asserts `get_graph_stats` reports symbols, `find_definition` resolves a fixture symbol and `search_code` returns the fixture file. The fixture is staged out of `engine/tests/` because the indexer deliberately filters `/tests/` paths out of the graph, so indexing it in place would only test that filter.
- **`test_metrics_persist.cpp` (new) — metric columns must survive a rebuild** (`engine/tests/`): the first index, a rebuild of a changed file, and a rebuild of an already-resolved database with nothing staged (the merged database of a parallel index) must all keep the same resolved row count *and* the same values, `metrics_ready` must agree with them, and no `_staged_metrics` row may survive. Disabling the fix makes all three rebuild cases fail.
- **`test_readme_ingestion.cpp` (extended)** (`engine/tests/`): a second project is indexed through a SUBDIRECTORY only, so the discovery walk cannot reach its root README; the enhance pass must ingest it exactly once, with the README's content, and a second enhance run must not duplicate the row.
- **Property-based tests** (`server/src/tools/clamp.rs`, `scheduler/worker.rs`, `mcp/protocol.rs`; `proptest` dev-dependency): clamping is asserted for *every* `i64` (never truncated by `as i32`, always inside the documented range), `CODESCOPE_EXCLUDE_PATHS` escaping round-trips through the C++ splitter's grammar (unescaped-comma split, `\,`/`\\` unescape), and MCP payloads carrying arbitrary text stay parseable JSON and round-trip byte-for-byte.
- **`test_engine_handles.cpp` (new) — the instance/boundary contracts code_rules §4 requires** (`engine/tests/`, registered by the existing test glob): rejected input (`NULL`, `""`, a path whose parent cannot exist) produces no instance; a null handle reaches both query shapes as the documented error envelope and does not crash; **two instances live in one process and keep separate stores** — a symbol indexed into one is invisible to the other, and destroying one leaves the other working; `engine_destroy(NULL)` is a no-op even when called twice. The suite's 4 Rust integration binaries declare their own `extern "C"` block, so the ABI change could only have been caught by the linker there; they now hold the handle through a small `engine_handle()` accessor (`test_graph_ffi_null.rs` passes a null one, which is what its null-store assertions always meant).
